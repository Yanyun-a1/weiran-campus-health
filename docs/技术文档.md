# 未然 · 校园健康 —— 省赛技术文档

## 摘要

本项目是面向校园健康场景的 Web 应用，把饮食、作息、运动三类状态数据与校医预约收进同一个小球视图，形成「关注 — 识别 — 预防 — 处置」的完整闭环。作品全程借助 AI 辅助编程工具（WorkBuddy）通过自然语言 Prompt 逐轮迭代构建，共 26 轮版本演进，最终代码为纯静态站点，无构建、无框架、无第三方运行时依赖。

本技术文档不按传统「功能模块说明书」组织，而是直接对应本赛项的三项文档要求与五项评分权重：**意图控制策略**（人如何设计上下文与 Prompt、如何驾驭 AI）、**架构设计**（AI 生成的代码采用什么架构、人如何约束它）、**可复现性论证**（开发全链路如何被确定性重现）。全文所述数字均可在公开仓库的逐轮日志、截图与哈希基线中逐条核对。

**关键词**：Vibe Coding、意图驱动编程、Prompt 工程、上下文管理、分层架构、可复现性、真浏览器 E2E

## 一、意图控制策略：如何设计上下文与 Prompt

> 对应评分维度「方法创新性与意图控制 20%」，并为「过程可复现性与演进链路 25%」提供原始证据。

### 1.1 人机分工模型

本项目确立了一条清晰的分工边界：**人负责定义问题、划定约束、判定验收；AI 负责生成代码、编写测试、定位缺陷**。这不是一句口号，而是被固化进每一轮对话的操作规程：

| 环节 | 人的动作 | AI 的动作 |
|---|---|---|
| 需求 | 写出带编号、可量化、带硬约束的规格 | 解析规格，核对现状，列出改动文件清单 |
| 实现 | 指定「只改哪些文件」「哪些一律不动」 | 以最小新增层实现，不回写核心文件 |
| 验证 | 决定「先测试」还是「直接发布」 | 写真浏览器 E2E，采集几何与 computed style |
| 缺陷 | 判断是断言写错还是代码真有问题 | 分别修断言或改产品代码，两类都留日志 |
| 交付 | 下达「更新发布」 | 部署后对线上同一链接复跑整套验收 |

关键设计：**验收权始终不交给 AI**。AI 可以报告「50/50 PASS」，但只有人决定是否发布；当人用截图反驳「还是有问题」时，AI 必须重新定位而非坚持已完成结论（见 1.6 与快照 chain-03）。

### 1.2 四段式 Prompt 范式

26 轮需求规格最终收敛成固定四段结构，这是本项目最核心的意图控制方法：

| 段 | 作用 | 真实示例（v28 原文摘录） |
|---|---|---|
| ① 改动范围 | 明确本轮能改什么、必须保留什么 | 「保留当前版本的同时做以下调整。两端一起改……两个改动互不影响」 |
| ② 硬约束 | 写死技术禁令，消除 AI 自由发挥空间 | 「不加 filter: drop-shadow，不加任何 glow」「不加 background-position 流动动画」「渐变只用蓝和青绿两个色相，不要引入紫色」 |
| ③ 验收标准 | 给可量化、可被机器判定的条目 | 「1440px / 1920px 下文字占容器 92%–96%」「距球底部边缘 6px」「三个标签互不重叠」「390px 和 320px 下都不超出屏幕」 |
| ④ 交付动作 | 明确本轮结束条件 | 「改完更新发布」／「改完先不要发布，给我测试」 |

四段式带来的直接收益是**每一条需求都能被翻译为一条断言**：v28 的 17 条验收标准最终对应 `e2e-v28.js` 的 50 条断言，本地与线上各 50/50 通过。相比之下，模糊表述如「做得好看一点」在本项目中不被接受，因为它无法判定。

### 1.3 上下文管理的三层机制

AI 在长会话中最典型的失效是「改 A 坏 B」。本项目用三层机制把上下文固定住：

**第一层 · 自然语言不可改清单。** 几乎每轮 Prompt 开头都写明「小球视图的投影公式、玻璃质感、三段式动画一律不动」「30 条问答、云数据库、医生列表、预约表单一律不动」。这不是礼貌性提醒，而是下一层机制的输入。

**第二层 · SHA256 基线锁。** 规格确定后，AI 先把「本轮不得改动」的文件逐一计算 SHA256 写入 `docs/baselines/vN-baseline.sha256`（v24–v28 每轮 20–23 个文件，涵盖 `faqs.js`、`tools/seed.sql`、`gate.js`、`orb-view.css` 等），改动完成后复算。E2E 脚本的第一条断言就是校验基线一致；不一致则整轮判定失败。这把「不要改」从自然语言约束升级为**机器可验证约束**。

**第三层 · 最小新增层协议。** 新需求一律通过新增独立 CSS/JS 层实现（`split.css`、`gate.css`、`polish.css`、`bg-v2.css`、`v25.css` … `v28.css`），按层叠顺序加载，后加层只覆盖自身职责。核心聚合文件只在结构性变更时才动，且改动前先核对 DOM 与投影实现。结果是：**小球逐帧投影公式、玻璃五层质感配方、三段式分裂动画自 v6–v8 定型后，在后续 20 轮迭代中零改动**。

### 1.4 五条真实 Prompt 链

赛项要求至少 3 条完整 Prompt 链，仓库 `docs/prompts/` 提供 **5 条**（含用户原始 Prompt 逐字全文、AI 文本回复原文、引导修 Bug 过程、产物与验收证据、复现命令），并附 68 条消息级原始摘录 `raw-excerpt.jsonl`：

| # | 轮次 | 链条类型 | 人的关键引导动作 |
|---|---|---|---|
| 01 | v6 | 缺陷根因诊断与架构重构 | 人直接写出「球变椭圆」的根因（transform 顺序把球体本身旋转），指定改法为 JS 每帧投影并要求「球永远是正圆」 |
| 02 | v14 | 上下文与不可改约束 | 用「投影公式、玻璃质感、三段式动画一律不动」框定 AI，要求「改完先不要发布，给我测试」 |
| 03 | v15 | 用户反馈闭环 | 人贴出运行截图反驳「已完成」结论，AI 重新定位为线上仍是旧版本与缓存，而非再改一遍样式 |
| 04 | v23 | 测试暴露真缺陷 | AI 主动报告两个真问题，人要求先定位再修改，拒绝把断言放宽了事 |
| 05 | v28 | 探针先测后定断言 | 17 条量化标准，AI 先跑几何探针实测再据此写断言，发布后线上复跑 |

三条最能体现「引导修复 Bug」的过程如下。

### 1.5 精讲一：从「球变椭圆」到逐帧投影（v6）

**缺陷**：v5 用 CSS 嵌套 3D 旋转实现球面，`transform` 顺序把球体本身也旋转，圆被拉成椭圆；同时渐变的 72%/86%/94% 停靠点落在可见圆之外，边缘光完全渲染不出来。

**人的引导**：没有说「修一下显示问题」，而是在 Prompt 中写出根因并指定架构级改法：「这一轮废掉 CSS 的嵌套 3D 旋转，改成 JS 每帧计算投影。球永远是正圆，只改变位置和大小」，同时划定「视觉风格、分裂动画、事件逻辑一律不动」。

**AI 的实现与三处判断**：AI 全量重写 `orb-view.js`（球面坐标 → 绕 Y → 绕 X → `k = d/(d−z2)` → 写 `--px/--py/--sc`），删除 `orb-view.css` 的全部 3D 变换。实现后主动报告三处需人决策的判断并给出实测依据：① 拖动符号取 `ry = dx*0.32` 而非字面 `-dx*0.32`，因为实测字面值会让左右拖方向与验收条目相反；② 外壳渐变必须加 `closest-side`，否则停靠点全在可见圆外；③ 深度 `opacity/filter` 写在 `.orb-skin`、`z-index` 写在 `.orb-item`，避免与分裂动画抢同一属性。

**验证**：`e2e-v6.js` 19/19；初始三球宽高比 1.0000；左拖时左球 175.5→155.1px、透明度 0.902→0.726、z-index 85→58，右球反向；390px 无溢出；全项目扫描确认无 `preserve-3d` / `perspective` / `rotateY` / `rotateX` / `translateZ`。此后的 20 余轮迭代再未回写该算法。

### 1.6 精讲二：用户截图反馈与「不盲目返工」（v15）

用户贴出真实运行截图并写「气泡最开始还是有问题」。AI 没有重做样式，而是先判断本地新样式已生效、线上仍是 v13 且浏览器拿到缓存资源，向用户说明「线上版本未更新」而非「代码有 bug」。用户随后下达「发布」，更新后恢复正常。这条链的价值在于：**人的验收权能够通过真实画面推翻 AI 的完成结论，而 AI 被要求先定位证据再动手**。同类机制在 v18 也生效——用户一句「点击校医院后预约校医不要跳出请假条」，AI 随即移除 `openLeaveForm(null)` 改为纯对话，避免两个入口功能重合。

### 1.7 精讲三：区分「断言写错」与「代码真缺陷」（v23 / v27）

AI 被明确要求对每一条 FAIL 先归类，再决定改哪里：

| 轮次 | 现象 | 归类 | 处理 |
|---|---|---|---|
| v21 | 26/27，脚本把 `isClear` 读成 `color`，采集写的是 `bg` | 断言写错 | 只修断言，产品代码不动 |
| v26 | ↑ 作为 flex 子项 computed 为 `block` 而非 `inline-block` | 断言写错 | 放宽断言并补真实 `transform` 采样 |
| v23 | 开启运行时错误捕获后发现 `updateStatus()` 因 `#modeHint` 已移除抛空指针 | 代码真缺陷 | 补空守卫；另修 `relRange()` 重复「今日/明日」前缀 |
| v27 | 抽屉收起 320ms 过渡期间 `place()` 误判球壳 rect，文案未恢复 | 代码真缺陷 | CSS 即时显隐 + 380ms 延时重算 |
| v23 | 线上分享链接会话抹掉 `?xtNow=`，冻结时钟失效 | 环境差异 | 冻结钩子同时写 `sessionStorage` |

v23 最终本地与线上各 **102/102**（8 个冻结时刻，含 23:59 跨午夜、03:20），真实时钟冒烟本地 3/3、线上 4/4。

### 1.8 意图冲突与规格取舍的记录机制

当规格内部冲突或要求写法不标准时，AI 被要求**如实报告取舍而非静默改写**，并写入交付说明：例如 `@//supports/` 按标准 `@supports not (-webkit-background-clip: text)` 落地；「12 小时内今日」与「不得出现过去时刻」冲突时，按下一次值班的实际日期判定；1023×768 横屏与抽屉展开态无可用空隙时，手机渐变文案自动淡出而非硬塞中点；1024px 触发 16px 字号下限并降级纯色以保单行。这些取舍全部留痕，构成可审阅的决策链。

### 1.9 可迁移的方法小结

四段式 Prompt + 不可改清单 + SHA256 基线 + 最小新增层 + 真浏览器断言 + 失败分类，六件事共同把「AI 写代码」变成一条**可审计的工程流水线**：每一轮都能回答「谁下的指令、AI 改了什么、哪些文件被锁住、用哪条断言证明、失败是断言还是代码、谁决定发布」。这正是本赛项「开发全链路可复现、从根本上杜绝抄袭与伪造」所要求的能力。

## 二、架构设计：AI 生成的代码采用什么架构，人如何约束它

> 对应评分维度「工程质量与架构设计 15%」。

### 2.1 总体架构

无构建、无框架的纯静态站点，四类组成：

| 层 | 文件 | 职责 |
|---|---|---|
| 结构层 | `index.html` | 顶栏、门禁、左右分屏 / 抽屉、球舞台、各类弹窗 DOM |
| 样式层 | 11 个 CSS 按版本顺序叠加 | 每层只覆盖本轮新增职责 |
| 逻辑层 | `config / evidence / faqs / campus-data / data-query / app / orb-view / gate / split / v26 / v27 / v28` | 配置、数据、问答、小球、门禁、双端布局、视觉增强 |
| 数据层 | 云端 `campus_faqs` + `faqs.js` 本地镜像 + `localStorage` | 30 条问答、门禁与预约记录 |

三个全局钩子 `XT_ORB = { recompute, highlight, focus }`、`XT_CHAT = { onMajor, onMid, bookDoctor }`、`XT_DRAWER = { open, close, isOpen }` 是跨模块联动的唯一接口，避免模块之间互相直接引用 DOM。

### 2.2 分层 CSS 叠加协议

加载链为 `styles.css → orb-view.css → split.css → gate.css → doctors.css → polish.css → bg-v2.css → v25.css → v26.css → v27.css → v28.css`。约束规则有三条：① 新层只写本轮新增选择器；② 需要覆盖旧规则时用更高特异性或明确标注的覆盖块，不改旧文件；③ 结构性 DOM 变更必须先在 E2E 中确认不影响既有 rect 与 computed style。这套协议让 26 轮迭代没有出现「改 A 坏 B」的回归。

### 2.3 核心算法：JS 逐帧球面投影

`orb-view.js` 的 `applyProjection()` 每帧把球面坐标做绕 Y、绕 X 旋转，用透视系数 `k = CAMERA_D / (CAMERA_D − z2)` 算出屏幕位移与缩放，写入 CSS 变量 `--px / --py / --sc`；深度参数 `t = (z2 + R) / 2R` 驱动 `opacity`、`brightness + blur` 与 `z-index`，从而用纯 2D 变换还原近大远小、近清远糊的立体层次，**不依赖 WebGL 或任何 3D 库**。球体本身只做 `translate3d(...) scale(...)`，永不旋转，因此永远是正圆。`requestAnimationFrame` 节流、松手 500ms 缓动回弹、位移 <8px 判定为点击而非拖动。

### 2.4 玻璃质感与三段式分裂

球面由五层叠加（中心透明 + 边缘亮环 + 顶部/底部高光 + 内阴影 + 环境光背景）构成；v18 起在球心加入「校医院」球，三个大类通过三条流动虚线汇聚到中心，表达「日常三域最终指向健康服务」。交互为三段式：大球层 → 九个子模块中球层 → 详情面板，逐级返回，配 `orbFlow` 虚线动画与 `orbHot` 脉冲高亮。

### 2.5 双端交互层

`matchMedia('(min-width: 1024px)')` 划分两套范式：桌面为左 380px 固定对话区 + 右球舞台；手机为全屏球舞台 + 底部 52px 把手、76vh 抽屉。抽屉用 `pointer` 事件 + `requestAnimationFrame` 拖拽、松手 30% 阈值、断点切换与本地记忆；`ResizeObserver` 处理窗口变化，`MutationObserver` 监听门禁状态。v28 的球下标签与大球共用同一组 `translate3d` 位移，但标签不套球的 `--sc`、不参与旋转、`z-index: -1` 低于球，进入中球层自动隐藏。

### 2.6 真实时间驱动的排班

`doctorState(d, now)`、`nextShiftStart(d, now)`、`floorHour(now)`、`relTime(d, now, base)`、`relRange(a, b, now)`、`bookingPreset(id, now)` 构成一组纯函数，依据系统当前时间推导医生在线状态、下一次值班起点、可约时段与凭证文字，处理跨午夜与「今日 / 明日 / 次日」格式；不在线医生也可提前预约。纯函数化使时间逻辑可被冻结时钟测试，这是 v23 能做到 102/102 的前提。

### 2.7 数据层与三层可用性兜底

云 SDK 走公网 CDN → 不通则用站内 `vendor/` 同版本副本 → 云数据库再不可读则降级到随站点发布的 `faqs.js` 本地镜像（同样 30 条）。前端用 `config.js` 中的**公开可发布密钥**直连 `/.cloud/database/rest/campus_faqs`，该表的行级安全策略为 `SELECT USING true`（公开只读），不依赖客户端登录态。预约记录只写浏览器 `localStorage`。

### 2.8 人如何用机器约束 AI

约束不是靠提示词反复强调，而是三道自动化关卡：`SHA256 基线`（不许改的文件一改即失败）、`几何探针`（布局类需求先用真浏览器实测再定断言阈值）、`双环境 E2E`（本地与线上各跑一遍，0 jsError 才允许发布）。因此「最小改动」是可验证事实，不是声明。

### 2.9 安全与隐私设计

全部业务数据为虚构脱敏模拟值，不接入真实校园系统、不收集真实个人信息；仓库不含任何 API secret / 令牌 / 口令 / 私钥；公开仓库中的密钥仅为设计上可公开的前端 publishable key，配合公开只读 RLS，不能写数据或提权；提供 `.env.example` 供评审替换为自有云实例。站点资源全部由云端返回，服务端文件无任何本地地址引用。

## 三、可复现性论证

> 对应评分维度「过程可复现性与演进链路 25%」——本赛项权重最高的维度之一。

### 3.1 10 分钟极速复现

```bash
git clone https://github.com/Yanyun-a1/weiran-campus-health.git
cd weiran-campus-health
python -m http.server 8123 --bind 127.0.0.1
# 浏览器打开 http://127.0.0.1:8123/index.html
# 演示账号 20260101 / 123456
```

无需构建、无需 `npm install`、无需安装数据库、无需申请密钥。云端不可达时自动降级到本地镜像，功能不中断。可选复跑：`node tests/e2e-v28.js`（本地 50/50）与带线上 URL 参数的同一脚本（线上 50/50），需本机 Chrome 带 `--remote-debugging-port=9222`。

### 3.2 环境配置、依赖清单与环境变量模板

| 类别 | 要求 |
|---|---|
| 运行时 | 无第三方依赖；`index.html` + CSS + 原生 JS |
| 本地服务 | Python 3.8+（仅标准库 `http.server`） |
| 浏览器 | Chrome / Edge 现代版（CSS 变量、`backdrop-filter`、`:has()`） |
| 测试（可选） | Node.js 18+（内置 `WebSocket` / `fetch`）+ CDP Chrome |
| 环境变量 | 见 `.env.example`；运行时**不需要任何私密凭据**，仅提供可选覆盖项 |

### 3.3 演进链与如实披露口径

仓库 `main` 共 **28 个 commit**：**27 个版本演进 commit**（v3→v28 共 26 轮迭代 + 1 个运维归档，提交日期取自各轮验收脚本的**真实文件时间** 2026-11-08 → 11-12）+ **1 个省赛材料补录 commit**（2026-11-17，仅文档与证据）。下文所称「演进链」均指前 27 个。

## 四、解题有效性与产品闭环

> 对应评分维度「解题有效性与实用价值 25%」。

### 4.1 痛点定义

校园健康服务存在一个具体而长期被忽略的错位：学生对饮食、作息、运动状态平时缺乏感知，往往到身体不适才第一次接触校医；而问答、请假、预约又分散在不同入口，切换成本高。结果是「预防」在制度上被反复强调，在产品上却没有可操作的落点——既没有一个让人愿意每天点开一眼的界面，也没有从「看到异常」直达「完成处置」的路径。

### 4.2 产品闭环

本作品把闭环压缩进同一个视图：**小球舞台承担探索与可视化，对话面板承担解释与事务办理，中心「校医院」球承担服务入口**。三者通过全局钩子联动，用户从「看一眼状态」到「约一次校医」不需要切换页面、不需要重新登录、不需要重新输入身份信息。

```
关注（三球状态投影） → 识别（分裂到子模块 / 看详情 / 问答解释）
      → 预防（内容卡与引导文案） → 处置（校医院球 → 医生列表 → 预约凭证）
                                      ↓
                            我的预约（可回溯记录）
```

### 4.3 功能清单

| 模块 | 内容 | 入口 |
|---|---|---|
| 三道门禁 | 登录、知情同意、首次推荐；本地记忆不重走 | 首次打开 |
| AI 对话 | 欢迎语 + 三快捷、意图路由、30 条问答（10 分类）、模块内容卡、请假条生成 | 桌面左栏 / 手机抽屉 |
| 小球视图 | 三大球（食序 / 息衡 / 动跃）→ 九个子模块三段式分裂、逐级返回、中心校医院球与三条虚线 | 桌面右栏 / 手机全屏 |
| 校医预约 | 医生列表、真实时间在线状态与可约时段、复用请假表单预填、预约凭证卡、我的预约 | 点中心球 |
| 双端引导 | 桌面渐变主文案；手机说明行 + 球下标签 +「去点球 →」按钮 | 各端首屏 |

### 4.4 双端使用路径

- **桌面（≥1024px）**：左 380px 对话区提问或点快捷入口 → 右栏点大球展开子模块 → 点中心校医院球 → 选医生填预约 → 对话流追加凭证卡 →「我的预约」查历史。
- **手机（≤1023px）**：全屏球舞台 → 底部把手上拉展开 76vh 抽屉 → 对话里点「去点球 →」收起抽屉并让对应球脉冲高亮 → 三大球下有「饮食 / 作息 / 运动」通俗标签，进入中球层自动隐藏。

### 4.5 真实时间驱动的业务价值

医生状态与可约时段不是演示用的写死示例，而是由系统当前时间实时推导：支持跨午夜、「今日 / 明日 / 次日」格式，不在线医生也可提前预约，提交后凭证文字与实际时段一致。这使原型在评审当天、跨天、凌晨等不同时刻打开都表现自洽，避免了「演示时才对」的常见缺陷。v23 用 8 个冻结时刻专项验收，本地与线上各 102/102。

### 4.6 数据与隐私边界、为何不接真实系统

全部业务数据为虚构脱敏模拟值：学生以「同学 A/B/C」代称，演示学号、医生姓名、排班时段、健康档案均为模拟值；不接入任何真实校园系统、不收集真实个人信息。这一选择有三重理由：① 遵守「全部使用脱敏模拟数据」的约束；② 避免真实健康数据带来的合规与授权成本；③ 让评审在任何一台电脑、任何网络环境下都能完整复现全部交互，不必依赖校方账号、内网或数据授权。

### 4.7 落地规划

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| 近期 | 试点可用 | 接入校医院真实排班接口与统一身份认证；预约记录从 `localStorage` 迁移到服务端并做数据脱敏 |
| 中期 | 场景扩展 | 增加健康趋势视图、班级/院系聚合看板（仅聚合统计、不展示个体）、换季提醒与常见问题主动推送 |
| 长期 | 运营闭环 | 与校园一卡通、教务作息数据做合规授权对接；建立效果评估指标（预约履约率、主动查看率）；按等保要求完善审计与权限分级 |

## 五、工程质量、用户体验与验证

> 对应评分维度「工程质量与架构设计 15%」「用户体验与产品精细度 15%」。

### 5.1 工程质量

模块解耦清晰（分层 CSS + 三钩子接口）、无第三方运行时依赖、无构建链路、无严重安全漏洞与性能死循环；核心算法纯函数化以便测试；每轮改动有 SHA256 基线与回归脚本兜底。`git fsck` 正常，仓库工作树无未提交变更。

### 5.2 性能守卫

拖动时 `:has(.drawer-open)` 暂停 `backdrop-filter` 与渐变动画，避免低端设备拖拽掉帧；逐帧投影用 `requestAnimationFrame` 节流；拖动停止后 500ms 缓动回弹。桌面主文案以 40px 为基准测量 `scrollWidth`，按容器 96% 反算字号，`resize` 时重算；窗口 <1200px 最低降到 16px，仍放不下则降级纯色但保持单行不换行；`@supports` 为不支持 `background-clip:text` 的环境提供纯色回退，`prefers-reduced-motion` 时停用流动动画。

### 5.3 体验细节

桌面主界面左对话右舞台的分区固定，手机抽屉支持把手区起手拖拽与 30% 阈值；分端方位词随断点实时切换；「去点球 →」把用户从聊天引导回可视化并让对应球脉冲；球下通俗标签降低新用户理解成本；AI 消息气泡采用 15px/1.65、胶囊不裁切、头像「未」；三道门禁只在首次出现。

### 5.4 已知取舍与改进方向

| 项 | 现状 | 说明 |
|---|---|---|
| 1023×768 横屏 / 抽屉展开 | 手机渐变文案自动淡出 | 该态下顶栏与球舞台之间无可用空隙，取自动淡出而非硬塞 |
| 点大球的高亮 | 需先返回大球层再脉冲 | 约多 560ms，属既定动画时序 |
| 桌面渐变 / 手机渐变 | 桌面 9s 流动，手机静态 | 静态才能在窄屏完整显示多段渐变 |
| iOS Safari | `background-attachment: fixed` 退化为 scroll | 浏览器行为差异，不影响功能 |
| 预约记录 | 仅浏览器本地 | 原型设定，落地阶段迁移服务端 |
